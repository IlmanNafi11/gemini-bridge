# Operations

Gemini Bridge is a single-operator, self-hosted service. It is not a multi-tenant boundary and should not be exposed directly to untrusted networks.

## Unofficial automation and account risk

Gemini Bridge drives the unofficial Gemini Web interface rather than a supported public API. Google may change the page, wire protocol, cookies, model behavior, or access policy at any time. Automated access may violate applicable terms of service, cause challenges or rate limits, flag an IP address, or suspend the account.

Use a dedicated account whose loss is acceptable. Do not use an organization-critical or personal primary account. Review the current terms yourself before operating the service. A valid setup today does not guarantee continued access.

## Network boundary

The default bind is `127.0.0.1:8090`. Keep that default unless a trusted reverse proxy or private network provides the external boundary. A non-loopback bind is rejected unless `server.api_key` is configured.

- Use a long random API key and deliver it through `BRIDGE_SERVER_API_KEY` or a root-readable environment file.
- Never place Google cookies or `BRIDGE_SECRET` in the TOML file, unit file, image, command line, logs, or source control.
- Terminate TLS at a trusted reverse proxy if traffic leaves the host.
- `/admin/*` and optional `/metrics` require the bearer API key.
- Keep CORS disabled unless a known browser client requires it.

## Credentials

Run `gemini-bridge auth login` and paste the complete browser `Cookie` header through standard input. The service stores `cookies.json` under the configured data directory with mode `0600` on Unix.

Set `BRIDGE_SECRET` before importing credentials to enable AES-GCM encryption at rest. The same secret is required for every later start. Losing the secret makes the stored cookie file unreadable; rotate credentials by deleting only `cookies.json` and importing again. File permissions and encryption do not protect credentials from a compromised process running as the service user.

Check session state with:

```bash
gemini-bridge --config /etc/gemini-bridge/bridge.toml doctor
curl --fail http://127.0.0.1:8090/healthz
curl http://127.0.0.1:8090/readyz
```

`/healthz` proves the process is serving. `/readyz` returns `503` for an unconfigured, stale, flagged, or reauthentication-required session. Never use `/healthz` alone as proof that Gemini requests will work.

## Data layout and retention

The default data root is `$XDG_DATA_HOME/gemini-bridge`, falling back to `~/.local/share/gemini-bridge`:

- `cookies.json` — sensitive Gemini session credentials; mode `0600` on Unix.
- `bridge.sqlite` — conversation and upstream identifier history.
- `media/` — content-addressed uploaded/generated bytes.
- `media/meta/` — JSON metadata, prompts, model names, and upstream file references.

Treat the entire directory as sensitive. Prompts, generated content, references, and conversation state may contain private data. Restrict it to the service account and include it in host backup/privacy policy decisions.

`storage.media_ttl_days` is configuration metadata for retention policy, but current media records without an expiry are retained until explicitly deleted. Use gallery deletion for individual records or the authenticated `POST /admin/purge` endpoint for records that have an expiry. Do not assume the configured number alone schedules deletion. Stop the service before manually deleting files so metadata and content do not diverge.

## Backup and restore

Back up `bridge.sqlite`, `media/`, and `media/meta/` together. Back up `cookies.json` only if the backup has equivalent access controls and the encryption secret is managed separately.

For a consistent offline backup:

1. Stop the service.
2. Copy the configured data directory while preserving ownership and permissions.
3. Restart and verify `/healthz` and `/readyz`.

Restore to the same data path and service user. If credentials are stale, remove `cookies.json` and run `auth login`; do not delete conversation or media data unnecessarily.

## systemd

Install the release binary and sample configuration, then adapt the checked-in unit:

```bash
sudo install -m 0755 target/release/gemini-bridge /usr/local/bin/gemini-bridge
sudo install -d -m 0750 -o gemini-bridge -g gemini-bridge /etc/gemini-bridge /var/lib/gemini-bridge
sudo install -m 0640 -o root -g gemini-bridge bridge.example.toml /etc/gemini-bridge/bridge.toml
sudo install -m 0644 deploy/systemd/gemini-bridge.service /etc/systemd/system/gemini-bridge.service
sudo systemctl daemon-reload
sudo systemctl enable --now gemini-bridge
```

Create `/etc/gemini-bridge/environment` with mode `0600` for `BRIDGE_SECRET` and `BRIDGE_SERVER_API_KEY`; do not use shell quoting in the file. The unit explicitly sets `BRIDGE_STORAGE_DATA_DIR=/var/lib/gemini-bridge` and `HOME` to the writable data directory.

## Container helper

The optional `Dockerfile` creates a non-root runtime image. BuildKit secrets or the orchestrator's secret store must supply `BRIDGE_SECRET` and the API key at runtime. Mount both configuration and durable data; never bake cookies into an image.

```bash
docker build -t gemini-bridge:local .
docker run --rm \
  -p 127.0.0.1:8090:8090 \
  -v "$PWD/bridge.toml:/etc/gemini-bridge/bridge.toml:ro" \
  -v gemini-bridge-data:/var/lib/gemini-bridge \
  -e BRIDGE_SERVER_BIND_ADDR=0.0.0.0 \
  -e BRIDGE_STORAGE_DATA_DIR=/var/lib/gemini-bridge \
  -e BRIDGE_SERVER_API_KEY \
  -e BRIDGE_SECRET \
  gemini-bridge:local
```

The image contains glibc runtime libraries and is not the musl-static release artifact. The release workflow separately builds the static musl archive.

## Upgrades and rollback

1. Read release notes and back up the data directory.
2. Download the archive and matching `SHA256SUMS` from the same release.
3. Verify the checksum before replacing the binary.
4. Stop the service, atomically replace the binary, start it, then check `/healthz`, `/readyz`, and one representative local API request.
5. Roll back by restoring the previous binary. Restore data only if a release explicitly documents an incompatible migration.

Do not run two service versions against the same SQLite and media directory concurrently.

## Observability and troubleshooting

Logs are JSON and include request audit records. Known credential patterns are redacted, but operators should still restrict log access and retention.

- Process not healthy: inspect service logs and bind conflicts.
- `/readyz` says `unconfigured`: run `auth login` as the service user.
- `/readyz` says `needs_reauth`: import a fresh browser cookie and run `doctor`.
- `/readyz` says `ip_flagged`: stop retry loops and review the configured proxy/IP path.
- Upstream schema failures: update only to a release containing a reviewed schema change.
- Disk growth: inspect `media/`, gallery records, and retention metadata; use API deletion rather than removing content files alone.

No deployment action is performed by the release workflow; it only builds and publishes artifacts for version tags.

## Release smoke

`tests/release_smoke_test.rs` starts the built binary against a temporary configuration, waits for `/healthz`, then asserts readiness, admin authentication, and the created SQLite store. Point it at any built artifact:

```bash
GEMINI_BRIDGE_SMOKE_BINARY=target/x86_64-unknown-linux-musl/release/gemini-bridge \
  cargo test --release --test release_smoke_test
```
